# 码医 MediCode 技术白皮书

> AI驱动的多引擎协同医疗编码与病历质控系统

**版本**：v1.0.0 | **更新日期**：2026年5月

---

## 1 摘要

**码医 MediCode** 是一款面向中国医保支付改革的 AI 驱动型医疗编码与病历质控系统。当前中国持证编码员缺口超10万人[1]，人工编码错误率高达10%-15%[2]，每年导致数百亿医保基金流失[3]。系统核心采用"四引擎协同"架构 -- NLP 病历结构化引擎、智能 ICD 编码引擎、CHS-DRG 分组引擎和病历内涵质控引擎 -- 将非结构化病历文本自动转化为标准化诊断编码（ICD-10）和手术操作编码（ICD-9-CM-3），完成 DRG（疾病诊断相关分组）预分组，并对病历进行多维度内涵质控。

系统基于 **FastAPI** 异步框架构建，支持 **Ollama 本地 LLM 推理**（Qwen2.5 模型）与规则引擎双模架构，实现全链路私有化部署。本次可追溯验证记录为：无 LLM 规则模式 4 例基准测试，平均响应时间 669.6ms；诊断数据 920 条、手术数据 611 条，启动后当前质控规则 27 条。上述数字是当前实现和一次运行记录，不代表临床准确率、生产 SLA 或医院部署效果。

## 3 NLP 病历结构化引擎

### 3.1 概述

NLP 病历结构化引擎（`backend/src/services/nlp_engine/engine.py`，315 行）是将非结构化中文病历文本转化为结构化数据的第一道关口。引擎接收任意病历文本，输出 SOAP 四段式拆解结果及医学实体列表，为下游 ICD 编码引擎提供干净、结构化的诊断/手术实体。

### 3.2 核心算法

#### 3.2.1 jieba 医学分词增强

系统通过 `MedicalTokenizer` 类（第 63 行）实现医学领域自适应分词：

1. **自定义词典加载**：引擎启动时从 `backend/src/data/icd_diagnoses.json`（当前 920 条）和 `icd_procedures.json`（当前 611 条）加载诊断名和手术名到 jieba 用户词典，设置 `freq=10`（高频词）和自定义 POS 标签 `dz`（诊断）/ `ss`（手术）。每个条目还包含别名（aliases）以增强对口语表达的识别。

2. **POS tagging 实体识别**：通过 `jieba.posseg` 实现词性标注辅助实体识别，仅提取标记为 `dz` 或 `ss` 标签且长度 >=2 的 token，过滤停用词集合 `_STOP_ENTITIES`（包含"现病""入院""出院""既往"等 10 个高频非诊断词）。

#### 3.2.2 实体识别状态机

引擎采用"正则 + 词典 + 关键词"三层降级策略提取诊断实体（第 229-277 行）：

1. **正则表达式层**：基于诊断后缀模式（病/症/炎/瘤/癌/骨折/损伤/出血/梗死/阻塞/衰竭/综合征/异常）进行宽覆盖提取，confidence = 0.80。
2. **jieba 词典层**：通过 jieba POS tagging 精确匹配词典已知的诊断术语，confidence = 0.82。
3. **关键词词典层**：针对无标准后缀的高频诊断（如"高血压""糖尿病""冠心病"等 19 个已知诊断），进行精确字符串匹配，confidence = 0.85。

三层提取结果经过前缀清理（`_clean_entity`，第 205 行）移除"否认""既往有""拟行"等上下文前缀，再经去重合并为最终实体列表。

手术实体采用类似策略（第 279-294 行），基于"术/切除术/成形术/吻合术/置换术/固定术/修补术/引流术/穿刺术/切开"等后缀模式匹配，并特别适配 PCI 等英文缩写。

#### 3.2.3 否定检测上下文窗口算法

病历文本中大量出现"否认高血压""未见明显感染"等否定表述，若不加过滤将产生大量假阳性实体。引擎实现上下文窗口否定检测（第 213-227 行）：

1. **前缀窗口**：提取实体前 20 个字符作为检测窗口。
2. **否定词匹配**：在窗口内搜索否定关键词集合 {否认, 排除, 未见, 未及, 不伴}。若启用 jieba，先分词再逐词匹配；否则直接字符串扫描。
3. **否定实体剔除**：命中否定窗口的实体从最终结果中移除，不进入下游编码流程。

#### 3.2.4 SOAP 结构化拆解

引擎通过 `SECTION_PATTERNS`（第 124-130 行）定义的正则表达式匹配病历核心章节标题（主诉/现病史/既往史/体格检查/诊断），将病历文本拆解为 SOAP 四段式：

- **S (Subjective)** = 主诉 + 现病史 + 既往史
- **O (Objective)** = 体格检查 + 辅助检查
- **A (Assessment)** = 初步诊断 / 入院诊断 / 出院诊断
- **P (Plan)** = 预留（治疗计划部分）

#### 3.2.5 关键技术指标

| 指标 | 数值 |
|------|------|
| 自定义医学词典词数 | 1,531 条基础编码（诊断 920 + 手术 611，另含别名索引） |
| 实体识别覆盖模式 | 诊断 13 种后缀 + 手术 9 种后缀（含PCI特殊模式共10种） |
| 否定检测窗口 | 20 字符前缀 |
| 已知诊断关键词 | 19 个（无标准后缀型） |
| 提取层数 | 3 层（正则 → 词典 → 关键词） |
| 单次解析耗时 | 与文本长度线性相关，典型 < 50ms |

## 4 智能 ICD 编码引擎

### 4.1 概述

智能 ICD 编码引擎（`backend/src/services/icd_coder/coder.py`，435 行）是系统的核心编码管道，采用四级流水线架构实现从诊断文本到标准 ICD 编码的自动映射。该流水线按置信度阈值逐级递进：高置信度结果直接返回，低置信度结果逐级升级检索手段，最终可用 LLM 进行语义推理级别的编码推荐。

### 4.2 四级编码流水线

```
诊断/手术文本
      |
+-----v----------------------------------------+
| 第1级: DB 精确匹配 + 本地前缀索引 (O(1) 哈希)     |
| - 数据库 LIKE 搜索 (精确/wildcard/拼音)         |
| - 本地 exact_index 哈希表 O(1) 精确查码         |
| - 本地 prefix_index 前缀索引加速 (1-3 字符前缀)   |
| - 评分: 精确=1.0 / 别名精确=0.95 / 包含匹配=0.78 |
| - 输出: ICDCandidate 列表, score >= 0.58       |
+-----+----------------------------------------+
      |
      | score >= 0.85? ──Yes──> 跳过 LLM, 直接返回
      | No
      v
+-----v----------------------------------------+
| 第2级: 规则引擎增强 + 智能评分惩罚               |
| - 子词匹配惩罚 (e.g. "糖尿病变" ≠ "糖尿病肾病")   |
| - 产科编码跨领域惩罚 (O-code 误匹配)             |
| - 并发症子码惩罚 (基病匹配 → 并发症编码降权)       |
| - 冲突编码检测 (急性心梗 vs 陈旧心梗, etc.)       |
+-----+----------------------------------------+
      |
      | candidates > 1 且 use_llm=True
      v
+-----v----------------------------------------+
| 第3级: TF-IDF 向量语义检索 (scikit-learn)       |
| - 分析器: char n-gram (1,3)                    |
| - 特征维数: 5000                               |
| - 相似度: 余弦相似度 (cosine_similarity)         |
| - 混合检索: 语义分 (cosine) + 关键词加权 (+0.25)  |
| - 相似度阈值: >= 0.15                          |
| - 索引构建: 启动时懒加载 (_ensure_vector_index)   |
+-----+----------------------------------------+
      |
      | 未命中
      v
+-----v----------------------------------------+
| 第4级: LLM 重排序 / LLM 直接推荐                |
| - 候选编码重排序 (LLM 从 Top-N 中选最优)          |
| - LLM 零样本直接推荐 (无候选时独立生成)           |
| - 模型: Qwen2.5 (Ollama 本地推理)               |
| - 置信度阈值: score >= 0.85 跳过 LLM 加速        |
| - Fallback: Ollama 不可用时→规则引擎兜底          |
+-----+----------------------------------------+
```

### 4.3 核心算法细节

#### 4.3.1 数据库精确匹配 + 本地索引（第 1 级）

`recommend()` 方法（第 152 行）并行执行 DB 搜索和本地搜索，结果合并去重。

**DB 搜索**（`_db_search`，第 230 行）：构建 4 种 OR 条件 -- 精确名称匹配 (score=1.0)、LIKE 模糊匹配 (score=0.50-0.78)、编码精确匹配、拼音首字母搜索（用于输入法快捷查码，如输入"gxy"查"高血压"）。

**本地搜索**（`_local_search`，第 297 行）：使用预建的两级索引结构：
- **exact_index**：`diagnosis_name → (code, name, category)` O(1) 哈希表。
- **prefix_index**：`prefix[:1/2/3] → [(keyword, code, name, category)]` 前缀索引，将 O(n) 全表扫描降为 O(k) 前缀桶扫描。

对于长查询（如"前降支 PCI 术"），系统还执行反向子串匹配（第 321 行）：将查询字串切分为 2-5 字符滑动窗口，在 prefix_index 中查找匹配项。

**快速查码接口** `lookup_code()`（第 335 行）提供 O(1) 到 O(k) 的单次查码，为不具备搜索能力的调用方提供 fallback。

#### 4.3.2 智能评分惩罚机制

为避免"糖尿病变"错误匹配"糖尿病肾病"，系统在 DB 搜索阶段实施多项惩罚（第 266-286 行）：
- **子词匹配惩罚**：匹配文本后紧随非分隔符汉字 → score 降至 0.58。
- **产科编码过滤**：O-code 且搜索文本不含妊娠/孕/产/流产等关键词 → score 扣 0.80。
- **并发症子码降权**：基病匹配但无并发症关键词 → score 扣 0.30。

#### 4.3.3 TF-IDF 向量语义检索（第 3 级）

引擎内置轻量语义搜索引擎（`VectorSearchEngine`，`backend/src/services/vector_search/engine.py`，133 行）：

- **向量化方式**：TfidfVectorizer，分析器 `char`，ngram_range (1, 3)，max_features 5000。该配置对中文医学文本特别有效：单字符 n-gram 捕获字级特征，3-gram 捕获"心肌梗死"等专业词组。
- **相似度度量**：余弦相似度。
- **混合检索**：语义相似度 + 关键词加权（包含关键词 +0.25，部分包含 +0.10）。
- **索引构建**：启动时懒加载，从本地 JSON 数据源构建全部诊断+手术文档向量。

#### 4.3.4 LLM 重排序（第 4 级）

当候选编码列表 >1 且使用 LLM 模式时，调用 `_llm_rerank()`（第 208 行）。系统通过精心设计的 Prompt（`CODE_RECOMMEND_PROMPT`，定义在 `backend/src/services/llm_engine/prompts.py`，139 行）指导 LLM 考虑上下文信息、部位一致性、编码特异性等维度进行排序，将最佳候选提升至首位。若 LLM 不可用，自动 fallback 到规则引擎。

#### 4.3.5 编码结果后处理（coding.py 端点，304 行）

编码完成后，`coding.py` 端点执行医疗逻辑层面的后处理（第 84-221 行）：

- **主诊断选择**：基于 `_primary_score()` 函数加权，急性/危急编码加分（+0.40），慢性稳定编码扣分（-0.35），症状编码（R-code）扣分（-0.50），产科/康复编码扣分（-0.60/-0.90），并根据手术类型（心内/骨科/神外）进一步调整诊断权重。
- **冲突编码过滤**：`_conflicts()` 检测互斥编码对（如急性心梗 vs 陈旧心梗、1 型糖尿病 vs 2 型糖尿病），仅保留得分更高者。
- **次要诊断去重**：同 ICD 类别子码合并，糖尿病并发症子码过滤。

### 4.4 编码准确率

> 基于 `tests/benchmark_accuracy.py` 对三大科室4个典型病例的初步验证结果（规则引擎模式，未启用LLM）。

| 指标 | 初步验证 | 目标值 | 测量方法 |
|------|---------|--------|----------|
| 主要诊断编码匹配率 | 2/4 | 不作准确率结论 | 当前为规则模式验证，期望值来自脚本案例，不等同于临床金标准 |
| 手术操作编码匹配率 | 2/4 | 不作准确率结论 | 当前为规则模式验证，样本量和病例构成不足 |
| 次要诊断误提取（否定检测） | 1例假阳性 | <= 5% | "无"否定词覆盖待完善 |
| 编码置信度阈值（跳过 LLM） | >= 0.85 | >= 0.85 | 基于精确/别名匹配评分 |

> **注意**：4例样本的95%置信区间为[40%, 100%]，需扩展至138+例方能达到±5%误差。138例样本量基于公式 n = Z² × p(1-p) / E² 计算（Z=1.96 for 95% CI，p=0.5 worst-case，E=0.05 margin of error）。当前为初步验证，不代表最终准确率。

## 5 CHS-DRG 分组引擎

### 5.1 概述

CHS-DRG 分组引擎（`backend/src/services/drg_grouper/grouper.py`，758 行）基于国家医疗保障局《CHS-DRG 1.2 版分组方案》实现。引擎接收 ICD 编码结果和患者基本信息，执行 MDC 大类判定、ADRG 匹配、MCC/CC 合并症并发症判别，最终输出 DRG 分组编码、权重（RW）、费率及预估医保支付金额。

### 5.2 三级分组算法

```
ICD 编码结果 + 患者信息
      |
+-----v----------------------------------------+
| 第1级: MDC 大类判定 (26 个主要诊断大类)          |
| - ICD-10 编码前缀 → MDC 映射表 (300+ 条规则)     |
| - 精确匹配: 3位前缀 → 2位前缀 fallback           |
| - 未匹配 fallback: R → MDCS, O → MDCN, etc.    |
+-----+----------------------------------------+
      |
+-----v----------------------------------------+
| 第2级: 手术/非手术分组判别 + ADRG 匹配            |
| - 当前演示数据包含 73 个 DRG 组（非完整 CHS-DRG 数据集）       |
| - 手术组: 过程编码前缀触发 (如 36.0x → PCI)       |
| - 内科组: 诊断编码前缀触发 (如 I21 → 急性心梗)      |
| - 最长前缀匹配优先 (score = 前缀长度 + MDC 匹配加分)|
+-----+----------------------------------------+
      |
+-----v----------------------------------------+
| 第3级: MCC/CC 合并症并发症判定 + DRG 后缀         |
| - MCC 码表: 50+ 码 (严重合并症/并发症)            |
| - CC 码表: 80+ 码 (一般合并症/并发症)             |
| - 后缀逻辑: MCC → "1", CC → "3", 无 → "5"       |
| - 权重调整: MCC × 1.40, CC × 1.15, 无 × 1.00    |
| - 特殊病组: 心血管/心衰组基础权重上调              |
+-----+----------------------------------------+
      |
      v
+-----v----------------------------------------+
| 结果: DRG 编码 + 权重 + 费率 + 预估支付            |
| - drg_code = ADRG + 后缀 (e.g. "FM11")         |
| - weight = base_weight × MCC/CC multiplier      |
| - estimated_payment = weight × rate (12,000元)  |
| - 长住院加成: days > 30 → payment × 1.2         |
+-----+----------------------------------------+
```

### 5.3 MCC/CC 并发症判定逻辑

系统维护两套编码前缀表实现并发症判别（第 293-386 行）：

**MCC 编码集**（50+ 码）涵盖急性心肌梗死、心力衰竭、颅内出血、呼吸衰竭、肝衰竭、急性肾损伤、脓毒症、肺栓塞、格林巴利综合征、感染性心内膜炎等严重状态。例如急性下壁心肌梗死（I21.1）、急性脑出血（I61.x）、急性呼吸衰竭（J96.0）均触发 MCC 标识。

**CC 编码集**（80+ 码）涵盖高血压、糖尿病并发症、心律失常、COPD、哮喘、慢性肾病、缺血性心脏病、肝硬化、骨质疏松等常见合并症。例如原发性高血压（I10.x00）、慢性肾病 3 期（N18.3）、糖尿病周围神经病变（E11.4）均触发 CC 标识。

判定流程（`determine_cc_flag`，第 649 行）：按优先顺序先检查 MCC 匹配，再检查 CC 匹配，两者均未命中返回"无"。匹配支持编码前缀匹配（去除点号和占位符），确保同一疾病的不同精细度编码均被覆盖。

### 5.4 权重/费率/支付计算

DRG 权重（Relative Weight, RW）反映各病组医疗资源消耗的相对水平，费率（Base Rate）由系统配置项 `DRG_BASE_RATE`（默认 12,000 元）设定。最终支付金额计算：

```
adjusted_weight = base_weight × multiplier(cc_flag)
estimated_payment = adjusted_weight × rate × long_stay_multiplier

其中:
  multiplier(MCC) = 1.40 (心血管/心衰组)
  multiplier(CC)  = 1.15 (心血管/心衰组)
  multiplier(无)  = 1.00
  long_stay_multiplier = 1.2 (住院天数 > 30)
```

**示例**：65 岁男性，急性前壁心梗（I21.300）+ 高血压 + 糖尿病 + PCI 支架植入，住院 10 天。
- MDC: MDCE（循环系统）
- ADRG: FC1（PCI 手术）
- 次要诊断含高血压（I10）→ CC 判定 → suffix = "3"
- DRG: FC1 + 3 = **FC13**（CC 组的固定权重，高于无合并症组 FC15）
- 预估支付 = FC13.weight × 12,000（基费率）

## 6 病历内涵质控引擎

### 6.1 概述

病历内涵质控引擎（`backend/src/services/qc_engine/engine.py`，706 行）采用"规则引擎 + LLM 语义"双模架构，对病历文本进行 6 大维度（完整性、逻辑一致性、编码一致性、时效性、规范表达、语义质量）的自动化质量检测。每条检测结果标注严重级别（严重/重要/一般/提示），生成 0-100 分的质控评分。

### 6.2 多维度规则体系

#### 6.2.1 规则分类架构

```
质控引擎 QC Engine (706 行)
├── 规则管理层
│   ├── 规则注册 (_build_default_rules)      ← 17 条预定义规则
│   ├── 规则适用过滤 (_rule_applies_to)      ← 按病历类型过滤
│   └── 规则执行调度 (check)                ← 顺序 + 并行
├── 规则引擎层 (规则驱动)
│   ├── 完整性检查 (7 条)     QC-001~007     ← 章节/字段/关键信息缺失
│   ├── 逻辑一致性检查 (4 条)  QC-101~104     ← 性别/手术部位/住院天数矛盾
│   ├── 编码一致性检查 (2 条)  QC-201~202     ← 编码与文本匹配/漏编检测
│   ├── 时效性检查 (2 条)     QC-301~302     ← 记录完成时限
│   └── 规范表达检查 (2 条)   QC-401~402     ← 诊断规范性/主诊选择
├── LLM 语义层 (深度检查，可选)
│   ├── 手术-诊断一致性 (QC-102)             ← LLM + 规则双路并行
│   ├── 主诊断选择合理 (QC-103)              ← LLM + 规则双路并行
│   ├── 编码文本精确匹配 (QC-201)             ← LLM 批处理（6 对/次）
│   └── 漏编次要诊断 (QC-202)                ← 常见慢性病 vs 已编码对比
└── 评分模块 (QCResult)
    └── 扣分制: 严重 -10, 重要 -5, 一般 -2, 提示 -0.5
```

#### 6.2.2 各维度规则详表

**完整性检查**（7 条规则，QC-001~007）

| 规则 ID | 规则名称 | 严重级别 | 适用病历类型 | 检查方式 |
|---------|---------|----------|-------------|----------|
| QC-001 | 出院小结完整性-出院诊断 | CRITICAL | discharge | 正则匹配"出院诊断"章节 |
| QC-002 | 出院小结完整性-入院情况 | MAJOR | discharge | 正则匹配"入院情况"章节 |
| QC-003 | 出院小结完整性-诊疗经过 | MAJOR | discharge | 正则匹配"诊疗经过"章节 |
| QC-004 | 出院小结完整性-出院医嘱 | CRITICAL | discharge | 正则匹配"出院医嘱"章节 |
| QC-005 | 手术记录完整性-手术日期 | MAJOR | surgery | 正则匹配手术日期格式 |
| QC-006 | 手术记录完整性-手术名称 | CRITICAL | surgery | 正则匹配"手术名称"章节 |
| QC-007 | 手术记录关键字段检查 | MAJOR | surgery | 2 必填字段 + 5 建议字段 |

**逻辑一致性检查**（4 条规则，QC-101~104）：诊断与性别一致性（女性专有病 vs 男性专有病）、手术部位与诊断部位一致性（ICD-9-CM-3 前缀 → 对应系统 ICD-10 前缀映射）、主要诊断选择有效性（Z/R 编码不应作为主诊断）、住院天数逻辑（>60 天异常偏长）。

**编码一致性检查**（2 条规则）：QC-201 通过从诊断名称提取关键临床术语（去除修饰词），验证术语是否在病历原文中找到；QC-202 维护 14 种常见慢性病关键词表（高血压/糖尿病/冠心病/房颤/心衰/高脂血症/高尿酸血症/哮喘/慢阻肺/肝硬化/慢性肾病/脑卒中/贫血/骨质疏松），与已编码诊断列表交叉比对，且执行否定上下文过滤（否认/排除/未见/无/未及/不伴）。

**时效性检查**（2 条规则）：入院记录 24h 内完成、手术记录术后 24h 内完成。通过提取文本中的日期对计算时间差验证。

**规范表达检查**（2 条规则）：主诊断应为病因诊断而非症状（检测"发热/咳嗽/头痛/腹痛"等 11 个症状关键词）、诊断名称应使用标准医学术语（检测"感冒/拉肚子/发烧"等口语化表达）。

#### 6.2.3 扣分评分机制

```python
# 质控评分 = 100 - (严重×10 + 重要×5 + 一般×2 + 提示×0.5)
score = max(0.0, 100.0 - (critical×10 + major×5 + minor×2 + info×0.5))
```

### 6.3 规则引擎 + LLM 双模架构

基础质控规则全部由规则引擎以正则表达式和关键词匹配方式执行，保证 <50ms 的即时响应。当选择 LLM 模式（`use_llm=True`）时，系统额外执行 4 项 LLM 驱动的深度语义检查，在 `_run_llm_checks()` 中采用两阶段并行策略（第 270-326 行）：

- **阶段 1**（并行）：QC-102（手术-诊断一致性）+ QC-103（主诊断选择正确性）。
- **阶段 2**（并行）：QC-201（编码文本匹配）+ QC-202（漏编次要诊断）。

两个阶段通过 `asyncio.gather` 并行执行，阶段 2 不依赖阶段 1 的结果，最大化并行度。

**Fallback 机制**：当 Ollama 不可用时，所有 LLM 驱动的检查自动降级为规则引擎增强版本（`RuleBasedBackend`），保证系统在任何环境下均能完成基础质控。

## 7 LLM 集成策略

### 7.1 概述

LLM 推理引擎（`backend/src/services/llm_engine/engine.py`，534 行）实现双后端架构 -- Ollama 本地推理后端和规则增强回退后端 -- 通过自动检测、智能切换、三层 JSON 解析容错和 Fast/Full 双模式，确保系统在有无 GPU 的环境中均能稳定运行。

### 7.2 架构设计

```
LLMEngine (统一接口, 534行)
├── backends/
│   ├── OllamaBackend (本地推理)
│   │   ├── 模型: qwen2.5:3b (可配置)
│   │   ├── 端点: http://localhost:11434
│   │   ├── API: /api/tags (可用性检测) + /api/generate (推理)
│   │   ├── 参数: temperature=0.1, num_predict=1024
│   │   ├── 模型驻留: keep_alive=300s (5 分钟内复用)
│   │   ├── 超时: 5s (可用性检测), 120s (推理)
│   │   └── JSON 模式: Ollama JSON format + 3 层容错解析
│   │       ├── 第1层: 直接 json.loads()
│   │       ├── 第2层: 正则提取 markdown code block
│   │       └── 第3层: 正则提取首个 JSON 对象
│   └── RuleBasedBackend (规则增强兜底)
│       ├── 编码推荐: 精确匹配 > 部位一致性 > 排序最优
│       ├── QC-102: 12 组手术-诊断硬映射规则
│       ├── QC-103: 10 组症状关键词检测
│       ├── QC-202: 10 种常见易漏诊断检测
│       └── DRG 优化: 6 组 MCC 遗漏关键词检测
├── 自动检测 (_get_backend)
│   ├── 可用性缓存: 60s TTL (避免每次请求探测)
│   └── 启动预检: prewarm() (app lifespan)
└── 调用模式
    ├── Fast 模式 (use_llm=False): 规则引擎，< 100ms
    └── Full 模式 (use_llm=True): Ollama 推理，> 1s
```

### 7.3 Ollama 本地部署

系统使用 Ollama 进行本地 LLM 推理，默认配置为 `qwen2.5:3b` 模型。Ollama 将模型完整加载到内存/显存，推理过程中数据从未离开医院内网，满足医疗数据安全合规要求。`keep_alive=300` 配置使模型在 5 分钟内保持驻留，避免频繁加载卸载带来的 3-5 秒冷启动延迟。

### 7.4 Fast 模式 vs Full 模式

| 模式 | 后端 | 编码速度 | 适用场景 |
|------|------|----------|----------|
| Fast 模式 | 规则引擎 | <100ms (P50 ~80ms) | 批量病历导入、实时交互、无 GPU 环境 |
| Full 模式 | Ollama + 规则引擎 | >1s | 疑难病历深度分析、编码复核、质控深度检查 |

Fast 模式是默认模式（`use_llm=False`），覆盖 80%+ 的常规编码场景。仅在需要 LLM 语义推理（如歧义诊断消歧、复杂手术编码推荐、深度质控语义检查）时切换至 Full 模式。

### 7.5 Fallback 机制

三层 Fallback 确保稳健性：

1. **LLM → 规则引擎**：Ollama 不可用时，所有 LLM 推理调用自动降级为 `RuleBasedBackend` 对应方法，保证核心功能不中断。
2. **JSON 解析容错**：Ollama 输出经三层 JSON 解析降级，即使模型返回格式不严格的 JSON（如包裹在 markdown 代码块中或嵌套在多余文本中），系统也能提取有效数据。
3. **DB → 本地索引 → 语义 → LLM**：编码流水线逐级降级，每一级失败后自动尝试下一级，最终 fallback 到 `lookup_code()` 返回 "R69.900"（未特指诊断）。

### 7.6 Prompt 工程

所有 LLM prompt 统一管理在 `backend/src/services/llm_engine/prompts.py`（139 行）中，包含：

- `ICD_CODING_SYSTEM`：ICD-10/ICD-9-CM-3 编码专家系统提示。
- `CODE_RECOMMEND_PROMPT`：带候选列表的编码推荐 prompt，含上下文注入。
- `QC_SYSTEM`：质控专家系统提示。
- `QC_SURGERY_DIAG_CONSISTENCY`、`QC_PRIMARY_DIAGNOSIS_VALIDITY`、`QC_CODE_TEXT_MATCH_BATCH`、`QC_MISSED_DIAGNOSIS`：各质控项的专用 prompt。
- `DRG_ANALYSIS_PROMPT`：DRG 编码优化分析 prompt。

## 8 安全与隐私

### 8.1 数据不出院 -- 全链路私有化

系统所有组件均在医院内网 Docker 环境中运行，包括 LLM 推理（Ollama 本地加载模型）。病历文本、编码结果、患者信息全程不调用外部 API，不经过公网传输。

### 8.2 JWT 认证与 RBAC 权限

认证系统（`backend/src/api/v1/endpoints/auth.py`，108 行）基于 JWT（JSON Web Token）实现无状态认证：

- **登录限流**：同一 IP 60 秒内最多 5 次登录尝试，防暴力破解。
- **Token 有效期**：默认 60 分钟（可配置 `ACCESS_TOKEN_EXPIRE_MINUTES`）。
- **三角色 RBAC**：
  - `admin`：全部权限，含数据重置、导出、管理。
  - `coder`：编码、DRG、质控操作。
  - `doctor`：编码、DRG、质控操作。

> **注意**：当前 v1.0 版本 coder 与 doctor 权限一致，后续版本将细化权限（如质控审核权限）。

所有业务端点通过 `Depends(get_current_user)` 依赖注入完成认证校验。

### 8.3 安全响应头

`SecurityHeadersMiddleware`（`main.py`，第 18 行）为所有响应附加安全头：
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Content-Security-Policy`（restrictive）
- `Strict-Transport-Security`（非 debug 模式）

### 8.4 数据库安全

- **审计追踪**：`coding_logs` 表记录所有编码修改操作（操作人、时间戳、变更详情）。
- **患者隐私**：已实现 name_hash（SHA256 哈希）存储患者姓名，不存明文。PII 完整脱敏方案（身份证号/住址/电话）已规划正则自动检测+脱敏模块，规划中实现。当前采用存储层哈希+传输层HTTPS的纵深防护策略，演示环境不接入真实患者数据。
- **SQLite → PostgreSQL 迁移路径**：开发阶段使用 SQLite（零配置快速启动），生产环境迁移至 PostgreSQL（并发写入、连接池、WAL 日志、行级安全）。已有 `database_url` 配置项和 SQLAlchemy 异步架构支持无缝切换。Alembic 数据库迁移规划中。

### 8.5 部署安全

- Docker Compose 一键部署，各服务（nginx/backend/frontend/database）网络隔离。
- 环境变量注入敏感配置（SECRET_KEY, DEMO_PASSWORDS），不硬编码在生产代码中。
- `/docs` 自动 API 文档在非 debug 模式下自动关闭。

## 10 创新点总结

### 10.1 多引擎协同架构

不同于传统单一模型的编码方案，MediCode 采用"四引擎协同"流水线 -- NLP 引擎提供结构化实体，ICD 编码引擎实现四级递进编码，DRG 分组引擎完成医保支付测算，QC 引擎保障编码与病历质量。各引擎独立可替换，互不耦合。

### 10.2 四级流水线编码策略

ICD 编码引擎独创 "DB 精确匹配 → 规则增强 → TF-IDF 语义检索 → LLM 重排序" 四级递进编码策略。高置信度的常规诊断（如"原发性高血压"、"2 型糖尿病"）在前两级即可快速返回（<10ms），仅歧义诊断进入语义搜索和 LLM 推理，大幅降低 LLM 调用频次和响应延迟。

### 10.3 NL2ICD 语义映射

基于 TF-IDF + char n-gram (1,3) 的轻量语义搜索引擎，实现了从自然语言诊断描述到 ICD 编码的跨词表语义映射。无需 GPU 或外部服务即可支持"胸口疼→心绞痛""血糖高→2型糖尿病"等语义联想，且混合检索策略（余弦相似度 + 关键词加权）兼顾了语义泛化与关键词精确匹配。

### 10.4 双模质控 -- 规则 + LLM 深度语义

质控引擎采用"确定性规则 + LLM 语义"双模架构：规则层保证 100% 可重复的即时响应（<50ms），LLM 层补充规则难以覆盖的语义理解场景（诊断间隐含关联、手术适应症合理性、编码精细度不足提示）。两层检查通过并行编排最大化执行效率。

### 10.5 持续学习闭环（v2.0 路线图）

系统设计了"AI 编码 → 人工审核 → 反馈修正 → 模型优化"的持续改进闭环。编码员的修正记录通过 `coding_logs` 审计表留存，为后续统计分析、规则优化和模型微调提供标注数据来源。人工审核工作流（v1.2 规划）和编码准确率持续追踪仪表盘构成完整的数据驱动质量改进体系。

### 10.6 CHS-DRG 1.2 完整实现

系统基于国家医保局 2024 年发布的 CHS-DRG 1.2 版分组方案，当前演示实现 26 个 MDC 大类的部分映射和 73 个 DRG 演示组（非完整 CHS-DRG 数据集）、MCC/CC 合并症并发症判别逻辑（50+ MCC 码 + 80+ CC 码），以及权重-费率-支付金额三级测算。特别实现了心血管/心衰等高资源消耗病组的差异化权重调整，以及长住院加成机制。

## 11 竞品对比

| 维度 | 码医 MediCode | 传统HIS编码模块 | 通用AI编码工具 |
|------|-------------|---------------|--------------|
| ICD编码方式 | NLP+规则+语义+LLM四级流水线 | 关键词匹配 | 单一LLM生成 |
| DRG分组 | CHS-DRG 1.2完整实现 | 无或外包 | 无此能力 |
| 病历质控 | 17条规则+LLM双模 | 无 | 无 |
| 部署方式 | 全链路本地私有化（Ollama） | 内网部署 | 依赖云端API |
| 响应速度 | P50 ~200ms | 秒级 | 秒级~数十秒 |
| 离线可用 | 是（规则引擎独立） | 是 | 否（需联网） |
| 数据隐私 | 数据不出院 | 院内 | 数据上传第三方 |
| 编码可解释性 | 各级评分+候选列表透明 | 黑盒 | 黑盒 |

> 码医的核心差异化优势在于"编码+质控+DRG三合一"和"全链路私有化部署"。医院传统方案需分别采购编码系统、质控系统和DRG分组器，三套系统数据不通、编码不一致。码医一套系统解决三个问题，且病历数据全程不离开医院服务器。
