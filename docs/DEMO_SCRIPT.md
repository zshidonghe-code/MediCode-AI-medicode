## 一、环境准备（Pre-flight Checklist）

> **重要**：比赛现场至少提前30分钟完成以下检查。不要等到上场前5分钟才开机。

### 1.1 硬件检查

| 检查项 | 要求 | 确认方式 |
|--------|------|----------|
| 笔记本电脑 | 充满电 + 插着电源适配器 | 电池图标显示100%且充电中 |
| 外接显示器/投影 | HDMI连接正常，分辨率不低于1920x1080 | 检查桌面是否完整显示在投影上 |
| 网络连接 | 不要依赖比赛场馆WiFi | 最安全的方案：**全程本机localhost，不需要外网** |
| 鼠标 | 有线鼠标（不要用蓝牙，现场干扰多） | 插上确认能用 |
| 散热 | 笔记本底部垫高，风扇口不被遮挡 | 现场可能有桌布，注意不要盖住出风口 |

### 1.2 后端启动

**项目根目录**：`C:\Users\Donghe\Desktop\04_MediCode码医\MediCode`

打开第一个终端窗口（建议用Windows Terminal或PowerShell），执行以下操作。

#### 步骤1：进入后端目录并激活虚拟环境

```bash
cd C:\Users\Donghe\Desktop\04_MediCode码医\MediCode\backend
.venv\Scripts\activate
```

**确认方式**：终端提示符前面出现 `(.venv)` 字样。

#### 步骤2：确认数据库文件存在

```bash
# 用 dir 确认 medicode.db 文件存在
dir medicode.db
```

如果文件不存在（首次启动或数据库被误删），不用慌——FastAPI启动时会自动创建数据库并播种演示数据。这会在启动日志中体现。

#### 步骤3：启动后端服务

```bash
uvicorn src.main:app --reload --host 0.0.0.0 --port 8000
```

**预期成功输出**（关键行）：

```
INFO:     Uvicorn running on http://0.0.0.0:8001 (Press CTRL+C to quit)
INFO:     Started reloader process
INFO:     Started server process
INFO:     Waiting for application startup.
INFO:     LLM backend: ollama  (或 rule-based，都不影响演示)
INFO:     Application startup complete.
```

**确认方式**：打开浏览器访问 `http://localhost:8000/health`，看到 `{"status":"ok"}`。

#### 步骤4：检查Ollama状态

```bash
curl http://localhost:11434/api/tags
```

或直接访问 `http://localhost:8000/health/llm`，看到：

```json
{"llm_available": true, "llm_backend": "ollama"}
```

**如果Ollama未运行**（返回 `{"llm_available": false, "llm_backend": "rule-based"}`）：

- 这不是致命问题。Ollama离线时，编码引擎自动降级为"数据库精确匹配+拼音搜索+向量语义搜索"三层模式，**编码功能完全正常**。
- 唯一的区别：LLM增强的重排序功能暂时不可用；当前没有足够数据量化它对准确率的影响。演示仍可按规则模式完成。
- 如果你想启动Ollama：新开终端，运行 `ollama serve`，等待模型加载。

在浏览器中依次完成以下检查（建议比赛前15分钟做）：

- [ ] `http://localhost:8000/health` → `{"status":"ok"}`
- [ ] `http://localhost:8000/health/llm` → 确认LLM状态（在线或离线，心中要有数）
- [ ] 登录系统：用户名 `coder`，密码 `123456`，能正常进入智能流水线页面
- [ ] 点击左侧菜单第1项"智能流水线" → 页面正常显示，有"快速演示"和"完整演示"两个按钮
- [ ] **【关键】预热Dashboard**：点击左侧菜单第5项"数据驾驶舱"，等待所有图表加载完成（约3-5秒，6个API并行请求）。然后切回"智能流水线"。该标签页保持打开在后台——Dashboard首次加载最慢，预热后切过去秒开。

**浏览器要求**：
- 使用Chrome或Edge最新版
- 缩放比例设为100%（Ctrl+0）
- **关闭所有书签栏、扩展栏**——让浏览器界面尽可能干净

- F11进入全屏模式（演示时）

### 1.5 备用方案总览

| 故障场景 | 影响 | 应对 |
|----------|------|------|
| Ollama离线 | LLM增强不可用，影响程度尚未单独评估 | 系统自动降级，演示流程不变。话术改为"系统即使在离线环境下也能通过知识库完成规则模式编码" |
| 后端崩溃 | 全功能不可用 | 迅速执行 `Ctrl+C` 停止 → 重新执行启动命令。数据库已持久化，重启<10秒 |
| 前端白屏 | 无法展示UI | 刷新页面（F5）。如果持续白屏，检查后端是否运行中 |
| 数据库损坏 | 全功能不可用 | 删除 `medicode.db` → 重启后端（自动重建+播种） |
| 投影不显示 | 评委看不到 | 提前准备好备用方案：评委用自己手机扫码看（需要局域网IP） |

## 二、Demo路径总览（5分钟时间轴）

```
00:00 ───── 00:30 ───── 01:30 ───── 02:30 ───── 03:00 ───── 03:30 ───── 04:30 ───── 05:00
  │          │           │           │           │           │           │           │
  │  Step 1  │  Step 2   │  Step 3   │  Step 4   │  Step 5   │  Step 6   │  Step 7   │
  │  登录    │  编码流水  │  质控结果  │  DRG算账  │  拒付预测  │  数据看板  │  总结     │
  │          │           │           │           │           │           │           │
  └─ 30秒 ──┴── 60秒 ───┴── 60秒 ───┴── 30秒 ───┴── 30秒 ───┴── 60秒 ───┴── 30秒 ───┘
```

**总体原则**：

1. **演讲者主导节奏**，操作员跟随——演讲者说到哪一步，操作员就点到哪一步。不是操作员带着演讲者走。
2. **所有点击都要果断**，不要犹豫不决。评委能看出来你在找按钮。
3. **不要解释你在操作什么**——那是演讲者的工作。你只管点。
4. **鼠标移动要平滑**，不要抖。评委盯着大屏幕看，抖动非常明显。

### Step 1：登录（时间：00:00 - 00:30）

**操作员动作序列**：

1. 确认浏览器已经在 `http://localhost:5173` 登录页面。
2. 演讲者开始说话时，光标放在"用户名"输入框上做好准备。
3. 听到演讲者说"各位评委好"的时候，开始输入。
4. 输入用户名：`coder`
5. 按Tab键跳到密码框，输入密码：`MediCode@2025Demo#Coder`
6. 点击蓝色"进入系统"按钮（或直接按Enter键）。

**预期结果**：页面跳转到 `http://localhost:5173/pipeline`（智能流水线页面）。

**页面特征确认**：
- 左侧深色导航栏，顶部有"码医 MediCode"品牌标志（蓝色渐变图标+文字）
- 导航栏第1项"智能流水线"高亮选中
- 主内容区标题"智能编码流水线"，副标题"一站式病历智能分析"
- 右上角有蓝色渐变"快速演示"按钮和白色"完整演示"按钮
- 下方有一个大的文本输入框（placeholder: "请粘贴住院病历内容..."）
- 底部有"开始智能分析"蓝色按钮

**话术配合**：

| 时间 | 演讲者话术 | 操作员动作 |
|------|-----------|-----------|
| 0:00-0:10 | "各位评委好，我是码医的项目负责人[姓名]" | 光标已在用户名框，开始输入admin |
| 0:10-0:20 | "码医解决的是DRG医保支付改革下，医院编码难、质控难、算账难的问题" | 输入密码，点击登录 |

### Step 2：智能编码流水线（时间：00:30 - 01:30）

**操作员动作序列**：

1. 确认当前在流水线页面（`/pipeline`）。
2. 听到演讲者说"请看这个合成病例示例"时，**点击"完整演示"按钮**（白色按钮，在"快速演示"按钮右边）。

   > **为什么选"完整演示"**：完整演示有打字机效果——病历内容逐字出现在输入框里。这个过程非常有视觉冲击力，能让评委感受到"AI正在实时阅读病历"。
   >
   > **备用方案**：如果现场紧张或时间紧迫，点"快速演示"跳过打字机效果，病历直接粘贴进去。

3. 点击后，输入框开始出现心内科的病历文本（打字机效果，逐字打印）。
4. 打字预计15-20秒。**关键缓冲**：如果打字在10秒内完成（速度快），操作员等待至0:50再让演讲者过渡到编码结果。如果打字超过25秒仍未完成，直接点"停止"→"快速演示"切到结果。演讲者备有1-2句弹性填充话术（见同步表备注）。
5. 顶部的步骤条（Steps组件）依次激活：
   - "智能编码"图标闪烁（Step 0 in progress）
   - "质控检查"图标闪烁（Step 1 in progress）
   - "DRG分组"图标闪烁（Step 2 in progress）
   - 最后全部打勾（Step 3 complete）

6. 分析完成后，页面展开显示三个结果卡片。

**预期结果——编码结果卡片**（第一个卡片）：

- 标题："智能编码结果"，蓝色图标，右上角显示本次处理时间（以实际页面结果为准）
- 诊断表格包含：
  - 主要诊断：**急性ST段抬高型心肌梗死** → 编码 **I21.0**（高置信度标记）
  - 次要诊断1：**高血压3级** → 编码 **I10.x03**
  - 次要诊断2：**2型糖尿病** → 编码 **E11.900**
  - 手术操作：**经皮冠状动脉药物洗脱支架植入** → 编码 **36.0700**

**话术配合**：

| 时间 | 演讲者话术 | 操作员动作 |
|------|-----------|-----------|
| 0:30-0:40 | "这是一份真实的急性心肌梗死出院病历。大家可以看到，AI正在实时解析这份病历" | 点击"完整演示"，打字机开始 |
| 0:40-0:55 | "系统首先自动提取了全部诊断——1个主要诊断、2个次要诊断——并精准匹配了ICD-10编码" | 打字进行中…… |
| 0:55-1:10 | "同时，手术操作也自动编码完成——经皮冠状动脉支架植入，准确匹配ICD-9-CM-3手术编码36.0700" | 编码结果卡片出现，光标移到主要诊断编码行，悬停高亮 |
| 1:10-1:25 | "系统已完成规则模式编码，处理时间以页面实际显示为准；这次验证记录的平均耗时为669.6毫秒" | 光标指向处理时间标签（右上角的"xxxms"） |
| 1:25-1:30 | "但这只是第一步。接下来，系统自动启动了病历质控检查" | 向下滚动，直到蓝色"质控检查结果"标题卡填充屏幕上方1/3处（约在编码结果下方两屏） |

**如果出错**：

| 错误 | 操作 |
|------|------|
| 打字机太慢 | 点击"快速演示"旁边的下拉框，将速度从"标准"改为"快"。或者如果已经在进行中，直接点"停止"，然后点"快速演示"重新来。 |
| 打字机卡住了 | 点"停止"按钮（红色），然后点"快速演示"按钮（跳过打字机直接分析）。 |
| 分析报错（"分析失败，请重试"） | 通常是因为后端连接断开。检查后端终端是否仍在运行。如果后端挂了，参考第五节"事故预案"。 |
| 编码结果不对 | 不要在演示时纠结。演讲者按照预期结果说，如果有偏差就说"系统正在学习优化中"。赛后修复。 |

### Step 3：质控结果展示（时间：01:30 - 02:30）

**操作员动作序列**：

1. 确认质控结果卡片已经出现在编码结果下方。
2. 卡片标题："质控检查结果"，左侧有一个半圆仪表盘显示质控评分。
3. 鼠标先指向质控评分（仪表盘数字），让评委看到分数。
4. 然后缓慢向下滚动，展示缺陷列表表格。
5. 表格包含列：级别（颜色标签）、检查项、问题描述、建议、操作按钮。
6. 光标逐行缓慢划过缺陷——给演讲者时间和空间逐条讲解。
7. 演示采纳/忽略操作：在任意一行的"采纳"按钮上点一下，弹出"已采纳"提示。

**预期结果——质控结果卡片**：

- 左侧仪表盘：质控评分（如85分或92分等），颜色根据分数（绿/橙/红）
- 右上角标签：各严重级别数量（如：严重 1，重要 2，一般 1，提示 2）
- 下方表格列出每条缺陷：
  - 严重级别（红色标签）：例如"主要诊断为症状而非病因"
  - 重要级别（橙色标签）：例如"诊断编码中的关键临床术语在病历文本中未找到"
  - 一般级别（金色标签）：例如"诊断名称口语化，建议使用规范术语"

**话术配合**：

| 时间 | 演讲者话术 | 操作员动作 |
|------|-----------|-----------|
| 1:30-1:40 | "码医的质控引擎在编码完成后立即启动。请看，系统给出了一个综合质控评分——这份病历有一些需要关注的地方" | 光标指向仪表盘评分 |
| 1:40-1:55 | "第一项，严重缺陷：主要诊断选择问题。系统发现病历中主要诊断表述不够规范，可能导致编码偏差" | 光标停在第一条（红色标签）行上 |
| 1:55-2:10 | "第二项，重要缺陷：编码一致性检查。系统发现编码中的一些关键术语在病历原文中找不到对应描述，提示可能存在编码与文本不一致" | 光标停在第二条（橙色标签）行上 |
| 2:10-2:20 | "我们的系统不只是发现问题，还能给出具体的修正建议——编码员可以直接点'采纳'来接受系统建议" | 点击某行的"采纳"按钮，看到"已采纳"提示 |
| 2:20-2:30 | "更关键的是，这些质控结果会实时反馈给编码引擎，形成质量闭环——这就是内涵质控和传统事后抽查的本质区别" | 光标向DRG结果区域移动 |

**如果出错**：

| 错误 | 操作 |
|------|------|
| 质控结果没有缺陷（满分100分） | 这是好事，话术改为"这份病历质量优秀，系统未发现缺陷"。不能强行说有缺陷——评委可能事后追问。 |
| 缺陷太多滚动不过来 | 不需要展示全部。挑前3-4条最醒目的（严重+重要级别），快速划过。 |
| 点击"采纳"没反应 | 可能是API没有返回qc_result的ID（pipeline保存失败）。直接跳过这个操作，光标移到下一个区域。 |

### Step 4：DRG分组与费用测算（时间：02:30 - 03:30）

**操作员动作序列**：

1. 确保DRG分组卡片和医保支付测算卡片都在视野中。如果屏幕不够高，可以稍微向下滚动。
2. DRG分组卡片在左边（占60%宽度），支付测算卡片在右边（占40%宽度）。
3. 先指向DRG分组卡片的核心数据：
   - DRG编码（大字，紫色）
   - 权重RW
   - 合并症标记（MCC/CC）
4. 然后指向右侧支付卡片的大数字（预估支付金额，绿色大字）。
5. 最后指向支付公式区域："RW x 费率 = 预估支付金额"，这个计算公式很直观。

**预期结果——DRG分组卡片**：

- DRG编码：例如 **FR11** 或页面实际返回的分组
- DRG名称：例如"经皮冠状动脉介入治疗"（PCI+STEMI对应FM1组）
- MDC大类：MDCE（循环系统疾病及功能障碍）

## 五、事故预案（Failure Recovery）

### 5.1 后端挂了

**症状**：前端页面操作无响应，F12控制台显示 `net::ERR_CONNECTION_REFUSED` 或 `500 Internal Server Error`。

**恢复步骤**（操作员执行）：

1. `Alt+Tab` 切换到后端终端窗口。
2. `Ctrl+C` 停止当前进程。
3. 重新执行启动命令：

   ```bash
   uvicorn src.main:app --reload --host 0.0.0.0 --port 8000
   ```

4. 等待看到 `Application startup complete.`。
5. `Alt+Tab` 切回浏览器，刷新页面（F5）。

**如果数据库损坏**（启动时报SQLite错误）：

```bash
# 1. 停止后端
# 2. 删除数据库文件
del medicode.db

# 3. 重新启动后端（会自动重建数据库并播种演示数据）
uvicorn src.main:app --reload --host 0.0.0.0 --port 8000
```

**时间成本**：约15-20秒。

**演讲者此时说什么**："各位评委可以看到，我们的系统架构设计充分考虑了高可用性……"（拖延时间）

### 5.2 网页加载慢

**症状**：点击菜单后页面白屏超过5秒。

**恢复步骤**：

1. 硬刷新：`Ctrl+Shift+R`。
2. 如果还是慢，打开Chrome开发者工具（F12），切换到Network标签，看哪个请求卡住了。
3. 通常卡住的请求是 `/api/v1/dashboard/*`（驾驶舱的6个并行请求）。
4. 如果确实很慢，演讲者可以稍微放慢语速，或者在页面上做更多讲解来填时间。

**预防**：驾驶舱页面建议提前在另一个标签页打开并加载好（`Ctrl+Tab` 切换即可，不用现场加载）。

### 5.3 LLM超时（Ollama响应慢）

**症状**：编码结果返回正常（因为是规则引擎+向量搜索），但QC结果不完整或显示默认值。

**恢复步骤**：

1. 不需要操作。系统设计上LLM是增强层而非必需层。
2. 演讲者话术自动调整为："系统即使在离线环境或医院内网环境下，也能通过内置的医学知识库和规则引擎完成规则模式编码——LLM是尚待单独评估的可选增强层。"
3. 演示完全不受影响——编码、质控、DRG分组这些核心功能都不依赖Ollama。

### 5.4 投影/外接显示不工作

**症状**：接上投影仪后，外接屏幕黑屏或无信号。

**恢复步骤**：

1. `Win+P`（Windows投影快捷键），选择"复制"或"扩展"。
2. 如果还是黑屏，检查HDMI线是否插牢。
3. 最后一招：让前排评委直接看笔记本屏幕（笔记本屏幕转过去），或者准备一个iPad/平板做屏幕镜像。

**预防**：比赛前一定要到现场测试投影。不同场馆的投影系统差异很大。

### 5.5 电脑死机/蓝屏（极端情况）

**恢复步骤**：

1. 演讲者继续说话，用口述描述系统功能（演讲稿背熟的情况下可以撑几分钟）。
2. 操作员强制重启电脑（长按电源键10秒 → 重新开机）。
3. 开机后按以下顺序快速恢复：
   ```bash
   # 终端1：启动后端
   cd C:\Users\Donghe\Desktop\04_MediCode码医\MediCode\backend
   .venv\Scripts\activate
   uvicorn src.main:app --reload --host 0.0.0.0 --port 8000

   # 终端2：启动前端
   cd C:\Users\Donghe\Desktop\04_MediCode码医\MediCode\frontend
   npm run dev
   ```
4. 浏览器打开 `localhost:5173`。

**时间成本**：约5-7分钟（电脑重启+后端启动+前端`npm run dev`+浏览器打开）。比赛窗口通常不足以完整重启，建议备好PPT截图作为Plan B，操作员直接切到PPT继续。

### 附录C：演示前快速自检脚本

将以下内容保存为 `check.bat`（放在项目根目录），演示前双击运行即可快速检查环境：

```batch
@echo off
echo ====== 码医 MediCode 赛前检查 ======
echo.

echo [1/4] 检查后端...
curl -s http://localhost:8000/health 2>nul
if %errorlevel% neq 0 (
    echo [FAIL] 后端未运行！请启动后端。
) else (
    echo [OK] 后端运行中
)
echo.

echo [2/4] 检查LLM...
curl -s http://localhost:8000/health/llm 2>nul
echo.
echo.

echo [3/4] 检查前端...
curl -s http://localhost:5173 2>nul
if %errorlevel% neq 0 (
    echo [FAIL] 前端未运行！请启动前端。
) else (
    echo [OK] 前端运行中
)
echo.

echo [4/4] 检查数据库...
if exist "backend\medicode.db" (
    echo [OK] 数据库文件存在
) else (
    echo [WARN] 数据库文件不存在，后端启动后会自动创建
)
echo.
echo ====== 检查完成 ======
pause
```
