# 码医 MediCode 2027 中国国际大学生创新大赛执行计划

> 版本：v1.0
> 制定日期：2026-07-15
> 目标赛事：中国国际大学生创新大赛（2027）
> 计划周期：2026-07-15 至 2027 年全国总决赛
> 状态：执行基线；赛道、组别和比赛日期以 2027 年官方通知及学校通知为准

## 1. 计划目的

本计划用于统一码医未来一年的参赛方向、时间线、阶段交付物和验收标准。

现阶段不以继续增加页面和功能数量为主要目标，而是把已经能够运行的产品，建设成一个具备以下条件的国赛项目：

1. 问题真实：能够证明病案编码、病历质控、DRG 分组和拒付风险预警确实存在用户需求。
2. 方案可信：系统结论可解释、可追溯，由专业人员完成人工复核和最终确认。
3. 指标可靠：使用经过授权、脱敏或合成并由专家审核的标准病例进行重复测试。
4. 团队真实：由学生团队主导，具有真实的人类技术成员、医学顾问和校内指导教师。
5. 演示稳定：核心演示路径在 30 秒内体现价值，Ollama 不可用时仍能以规则模式完成演示。
6. 材料合规：所有数据、成果、合作、知识产权和商业结论均有证据，不夸大、不虚构。

## 2. 参赛方向

### 2.1 暂定赛道与组别

- 暂定赛道：高教主赛道。
- 项目方向：新医科与人工智能交叉应用。
- 暂定组别：本科生创意组。
- 确认条件：负责人、成员身份、项目注册情况和成果归属符合 2027 年正式资格要求，并取得学校竞赛负责部门确认。

如果正式资格不满足本科生创意组要求，只调整参赛组别和材料口径，不改变本计划的产品验证、医学证据和演示主线。

### 2.2 一句话定位

> 码医是一套面向住院病案提交前环节的智能编码与医保合规辅助系统，帮助编码员发现编码、病历质量、DRG 分组和拒付风险问题，并由人工完成最终确认。

### 2.3 方向边界

码医聚焦“提交前辅助审核”，不宣称：

- 代替医生诊断或治疗决策；
- 代替编码员进行无人审核的最终编码；
- 在未经验证的情况下达到某个准确率；
- 已经在医院正式部署、产生收入或减少损失；
- 拥有尚未取得的专利、软著、合作协议或客户。

### 2.4 核心竞争力

项目最终需要形成四类可验证优势：

| 优势 | 需要形成的证据 |
|---|---|
| 一体化工作流 | 同一份病历完成 ICD 建议、质控、DRG 和拒付风险检查 |
| 可解释与可复核 | 每项建议能够追溯到病历原文、规则或医学依据，并支持人工确认 |
| 私有化与可降级 | 支持内网部署；模型不可用时自动使用规则引擎完成核心流程 |
| 医学与业务价值 | 标准病例测试、专家评审、真实用户访谈及试用反馈 |

## 3. 当前基础与关键缺口

### 3.1 已有基础

- 已具备“登录 -> 病历 -> 编码 -> 质控 -> DRG -> 拒付风险”的核心演示链路。
- 已具备 Ollama 不可用时的规则模式兜底能力。
- 当前后端测试、前端测试、Lint 和生产构建已有可重复的验证命令。
- 已形成商业计划、路演、技术白皮书、演示脚本等初始材料。

已有材料仅作为草稿使用，其中的状态、数据和结论必须重新核验，不能直接作为 2027 年参赛事实。

### 3.2 必须补齐的缺口

| 优先级 | 缺口 | 完成标准 |
|---|---|---|
| P0 | 赛道、组别和资格尚未确认 | 学校竞赛负责部门给出明确答复并留存记录 |
| P0 | 缺少真实医学或病案编码顾问 | 至少 1 名专业人员持续参与病例审核和规则评审 |
| P0 | 缺少标准病例集和可信基准 | 建立可重复测试的病例金标准与首份基准报告 |
| P0 | 人类技术团队不足 | 至少 1 名真实学生技术成员承担并能答辩核心技术工作 |
| P1 | 缺少真实用户与试用证据 | 完成结构化访谈，并争取试用意向或合作证明 |
| P1 | 缺少完整人工复核闭环 | 建议可确认、修改、驳回并保留审计记录 |
| P1 | 旧材料存在无来源结论 | 建立主张证据台账，无依据内容删除或改为待验证假设 |

Codex 和其他 AI 工具只能作为研发辅助工具，不作为参赛成员、技术负责人或医学专家写入材料。

## 4. 总体资源分配

| 工作线 | 建议投入 | 目标 |
|---|---:|---|
| 医学证据与效果验证 | 35% | 病例金标准、专家审核、指标、错误分析 |

## 5. 时间线与阶段门槛

### 阶段一：定位、资格与团队（2026-07-15 至 2026-08-15）

目标：先解决“以什么身份参赛、由谁完成、解决什么问题”。

主要工作：

1. 联系学校创新创业或竞赛负责部门，确认预计赛道、组别、报名主体和校内时间。
2. 确认现有代码、文档、数据、名称和后续成果的归属。
3. 招募至少 1 名学生技术成员、1 名病案编码或 DRG 专业顾问，并明确校内指导教师。
4. 固化一句话定位、目标用户、使用场景和不做事项。
5. 审计现有材料中的准确率、市场规模、医院损失、收入、客户和知识产权表述。
6. 建立“主张证据台账”，记录每项对外结论的来源、责任人、状态和可使用范围。

交付物：

- 资格确认记录；
- 团队名单与职责表；
- 项目定位说明；
- 知识产权与数据来源清单；
- 主张证据台账 v1；
- 医学顾问参与确认与职责记录。

验收门槛：

- [ ] 学校确认暂定赛道和组别；
- [ ] 项目负责人、学生技术成员、医学顾问和指导教师均已确认参与，并接受明确分工；
- [ ] 所有核心宣传数字均标记为“已验证、待验证或禁止使用”；
- [ ] 团队能够用同一套表述说明目标用户、核心问题和产品边界。

### 阶段二：病例金标准与技术基准（2026-08-16 至 2026-10-31）

目标：把“系统能够运行”升级为“系统效果能够被可信地测量”。

主要工作：

1. 设计病例金标准格式，至少覆盖诊断、手术、编码、质控、DRG、拒付风险和依据。
2. 使用合成、公开、授权或严格脱敏病例；记录来源、授权和处理方式。
3. 由医学顾问审核标准答案、争议项和不适合自动判定的项目。
4. 先完成 10 例小样本流程验证，再扩展至 30 至 50 例。
5. 分别统计编码建议、质控发现、DRG 结果、拒付风险、耗时和失败率，不使用笼统的单一“准确率”。
6. 记录假阳性、假阴性、规则失败、模型失败和人工争议，形成错误分类。
7. 连续执行 10 次核心演示，并验证模型不可用时的规则降级路径。

交付物：

- 病例金标准数据字典；
- 30 至 50 例病例集；
- 专家审核记录；
- 基准报告 v1；
- 错误分类与改进清单；
- 演示稳定性记录。

验收门槛：

- [ ] 病例来源、脱敏方式和使用权限可说明；
- [ ] 每个标准答案均有审核状态和依据；
- [ ] 测试可由其他团队成员重复执行；
- [ ] 核心链路连续运行 10 次无阻断；
- [ ] Ollama 不可用时核心流程仍可完成；
- [ ] 报告同时披露优势、错误和样本局限。

### 阶段三：真实用户与场景验证（2026-11-01 至 2026-12-31）

目标：证明产品不是团队臆想，而是对应真实工作流程和真实痛点。

主要工作：

1. 访谈病案编码员、病案室、医保办、临床科室或医院信息部门。
2. 使用统一访谈提纲记录现有流程、耗时、错误类型、责任边界和采购约束。
3. 不只收集正面评价，同时记录反对意见、不可用场景和合规障碍。
4. 根据证据确定最优先用户和最小落地场景。
5. 争取至少一份专家评审意见、试用意向、合作备忘或合规的试用反馈。
6. 用访谈和试用数据校正商业计划，不直接套用行业平均数字。

交付物：

- 结构化访谈记录；
- 需求优先级与用户画像；
- 真实工作流图；
- 专家评审或试用证明；
- 商业假设修订记录。

验收门槛：

- [ ] 完成不少于 10 次有效访谈，且至少覆盖 3 类岗位；
- [ ] 明确一个首要用户和一个首要使用场景；
- [ ] 至少一名专业人员对问题和方案给出书面意见；
- [ ] 所有价值测算均能追溯到访谈、试验或公开权威数据。

### 阶段四：人机协同产品闭环（2027-01-01 至 2027-02-28）

目标：把比赛 Demo 升级为符合真实责任边界的辅助工作系统。

优先功能：

1. 编码和质控建议支持人工确认、修改、驳回及原因记录。
2. 建立操作审计记录，能够还原建议、人工处理和最终结果。
3. 每项关键建议显示病历原文、命中规则或其他可解释依据。
4. 增强患者隐私脱敏和敏感信息展示控制。
5. 固化离线部署、规则降级、数据备份和演示恢复方案。

可能涉及的功能文件在进入具体任务前单独列清单确认；本计划不提前授权修改公共鉴权、公共配置或无关模块。

交付物：

- 人工复核闭环；
- 建议证据链；
- 操作审计记录；
- 隐私与数据处理检查表；
- 离线演示和恢复手册；
- 基准报告 v2。

验收门槛：

- [ ] 一份病例能够从导入走到人工确认和归档；
- [ ] 关键建议可追溯，争议结果可人工修正；
- [ ] 系统不把 AI 建议展示为无需审核的最终医学结论；
- [ ] 演示环境断网、模型不可用或重启后存在可执行恢复路径；
- [ ] 新增行为具有对应自动化测试或最小验证记录。

### 阶段五：参赛材料与校赛准备（2027-03-01 至官方报名启动）

目标：形成能够提交、能够演示、能够答辩的第一套完整材料。

主要工作：

1. 重写商业计划书，所有事实、指标和案例与证据台账一致。
2. 制作路演 PPT，围绕问题、方案、创新、验证、团队、价值和规划展开。
3. 准备 30 秒、60 秒和 3 分钟演示版本，以及完整现场演示脚本。
4. 更新技术白皮书、系统架构、测试报告、隐私说明和部署方案。
5. 建立高频答辩题库，覆盖医学、技术、商业、团队、合规和竞争问题。
6. 邀请不同背景的老师和专业人员进行至少 3 轮模拟答辩。

交付物：

- 商业计划书 v1；
- 路演 PPT v1；
- 现场演示及备用视频；
- 技术与测试附件；
- 答辩题库及模拟答辩记录；
- 参赛材料一致性检查表。

验收门槛：

- [ ] 所有对外数字均能在证据台账中找到来源；
- [ ] PPT、商业计划书、Demo 和口头表述不存在冲突；
- [ ] 完成至少 3 轮模拟答辩并关闭高风险问题；
- [ ] 非技术评委能在 30 秒内理解用户、问题和产品价值；
- [ ] 团队每位成员都能解释自己的真实贡献。

### 阶段六：报名、校赛与省赛（以 2027 年正式通知为准）

目标：按正式规则完成报名，并用评审反馈持续加强证据。

主要工作：

1. 在通知发布后 48 小时内核对赛道、组别、成员、材料格式和截止时间。
2. 建立学校截止时间、官方截止时间和内部截止时间三套节点，内部节点至少提前 7 天。
3. 校赛后只处理评委反复提出的高价值问题，不进行无关的大规模改版。
4. 每轮比赛后更新问题清单、证据台账、演示脚本和答辩题库。
5. 省赛前完成一次完整环境重建和离线演示验证。

验收门槛：

- [ ] 报名信息与证明材料完全一致；
- [ ] 所有材料在内部截止时间前完成审核；
- [ ] 每条评委意见均有接受、拒绝或待验证的明确处理结论；
- [ ] 核心演示连续 10 次无故障；
- [ ] 备用电脑、离线版、视频和静态材料均可用。

### 阶段七：全国总决赛冲刺（以正式赛程为准）

目标：冻结可靠版本，把主要精力用于证据表达和现场稳定性。

主要工作：

1. 总决赛前 30 天进入冲刺期，只接受影响比赛结果的 P0/P1 任务。
2. 总决赛前 14 天冻结代码、病例、PPT 和演示数据。
3. 完成不少于 10 轮全流程计时彩排，覆盖正常、断网、模型不可用和设备异常。
4. 准备现场版、离线版、录屏版、静态截图版四级演示方案。
5. 对医学真实性、指标可信度、学生贡献和商业可行性进行最终交叉审查。

验收门槛：

- [ ] 版本冻结后不再加入展示性新功能；
- [ ] 全员在规定时间内完成陈述、演示和答辩；
- [ ] 任一关键设备或在线服务失败时可以在 30 秒内切换方案；
- [ ] 所有提交文件、演示内容和现场回答使用同一事实基线。

## 8. 工程任务执行纪律

后续代码修改严格按小步推进，一次只处理一个明确问题，不跨越过大的功能边界。

每个任务开始前必须列出：

1. 需要修改的文件或功能；
2. 每个文件或功能的具体修改点；
3. 可能影响的功能；
4. 需要新增或修改的测试；
5. 风险点和回滚方式。

每个任务必须遵守：

- 只修改与当前任务直接相关的文件；
- 不修改公共鉴权、公共配置和无关模块，除非用户为该任务单独授权；
- 不引入新的第三方依赖；
- 不格式化无关文件；
- 每完成一个问题，立即运行构建、Lint、测试或最小验证命令；
- 验证失败时停在当前问题，不继续叠加下一项修改；
- 完成后列出全部变更文件和实际执行的验证命令；
- 保留可回滚的小提交，不把多个不相关问题合并到一个提交中。

最低验证矩阵：

| 变更类型 | 每步最低验证 | 阶段结束验证 |
|---|---|---|
| 后端业务逻辑 | 相关单测或单个测试文件 | `python -m pytest tests -v`、`ruff check src`，必要时 `mypy src` |
| 前端交互 | 相关前端测试或目标页面最小验证 | `npm run lint`、`npm run build`、前端测试 |
| API 或跨端流程 | 相关 API 测试 | 核心演示链路端到端验证 |
| 规则或病例数据 | 目标病例回归 | 全量金标准基准对比 |
| 纯文档 | Markdown 结构、链接和 Git diff 检查 | 事实与证据台账一致性复核 |

## 9. 指标体系

所有指标必须同时标注样本量、数据来源、版本、评价人和测试日期。

### 9.1 产品效果

- ICD 建议：Top-1、Top-3 命中率，以及诊断和手术编码分别统计。
- 质控：按问题类型统计精确率、召回率、假阳性和假阴性。
- DRG：可评价病例的一致率，并单列信息不足或规则不覆盖病例。
- 拒付风险：风险类型覆盖率、专家认可率和误报率。
- 人工效率：单病例处理时间、人工修改次数和建议采纳率。

### 9.2 工程质量

- 核心演示成功率；
- 规则降级成功率；
- 关键 API 响应时间；
- 自动化测试通过率；
- 从空环境恢复到可演示状态所需时间。

### 9.3 竞赛准备

- 有效用户访谈数量及覆盖岗位；
- 专家审核病例数量；
- 有证据支撑的对外主张比例；
- 模拟答辩完成次数及未关闭高风险问题数；
- 团队成员对自己负责模块的独立讲解通过率。

## 10. 风险、触发条件与回滚方式

| 风险 | 触发条件 | 处理与回滚方式 |
|---|---|---|
| 参赛组别不符合 | 学校或正式通知确认不满足暂定组别 | 调整组别和材料口径；保留技术、验证和证据主线 |
| 缺少医学专家 | 2026-10-31 前仍无专业人员持续参与 | 停止使用“临床验证”表述，定位为待专家验证的辅助原型 |
| 缺少真实试用 | 2027-01-31 前无医院或真实用户试用证据 | 继续按创意组准备，不宣称落地、收入或规模化应用 |
| 病例数据不合规 | 无法证明来源、授权或脱敏过程 | 从数据集和演示中立即移除，回退到合成或公开病例 |
| 指标不可复现 | 无法说明样本、版本、方法或标准答案 | 撤下该指标，回退到已验证的基准版本 |
| 模型服务不可用 | Ollama 超时、离线或硬件不足 | 自动切换规则模式，并使用离线版或录屏版完成演示 |
| 新功能破坏主链路 | 构建、测试或核心演示失败 | 回滚当前小提交，恢复上一稳定标签，不叠加后续任务 |
| 材料之间口径冲突 | PPT、计划书、Demo 或答辩数据不一致 | 以主张证据台账为唯一事实源，统一修订后再发布 |
| 团队贡献无法证明 | 成员无法解释所负责成果 | 重新分工并保留过程记录；不把 AI 工具成果冒充成员贡献 |
| 赛程发生变化 | 2027 年通知与预估月份不同 | 以正式截止时间倒排，优先保留资格、证据和稳定演示任务 |

## 11. 决策与复盘节奏

- 每周：15 至 30 分钟任务复盘，更新阻塞项、证据台账和下一周唯一最高优先任务。
- 每月：按阶段验收门槛检查，未通过门槛时不扩大功能范围。
- 每个季度：由指导教师、医学顾问和团队进行一次方向审查。
- 每轮比赛后：在 48 小时内整理评委问题，区分事实问题、表达问题和方向问题。

优先级顺序始终为：

1. 资格与真实性；
2. 医学与数据合规；
3. 可验证的效果证据；
4. 核心演示稳定性；
5. 产品闭环；
6. 材料表达；
7. 非核心功能和视觉装饰。
